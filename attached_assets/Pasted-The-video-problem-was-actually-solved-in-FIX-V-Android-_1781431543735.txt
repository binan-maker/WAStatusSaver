The video problem was actually "solved" in FIX V — Android 11+ videos no longer use ExoPlayer at all, they just show a thumbnail and an "Open in Player" button. So video freezes should be gone.

Why it still stucks entirely
The freeze you're seeing is most likely not video anymore — it's the image loading and the SAF scan itself:

The BFS crawler walks the folder tree via SAF to find .Statuses. On MIUI/OneUI this can take 1–8 seconds. During that time, if any SAF call partially blocks the JS thread, the whole screen is frozen.

Images still go through content:// SAF URIs. When the viewer opens an image, expo-image has to stream from a SAF provider. On some OEM builds this stalls.

The withTimeout wrapper only helps if the SAF call is slow but async. If the Android SAF DocumentProvider blocks the Binder IPC thread (which happens on certain MIUI versions), the timeout cannot save you because the JS event loop itself is stuck.

The complexity tax — 15+ early-return guards, multiple ref systems, polling loops, and serial queues all running together create unpredictable interaction bugs that are very hard to trace without a real device attached to a debugger.

Should you rewrite the whole app or just fix parts?
Do NOT rewrite the whole app. The payment system, referral system, ads, UI screens, auth — all of that works perfectly on both Android versions. A full rewrite would take weeks and you'd face the exact same SAF problem again.

What actually needs a targeted rewrite is only the storage access layer — specifically MediaContext.tsx's SAF path and the viewer's image loading for Android 11+. This is about 400–600 lines of the 1,912-line file.

The real architectural fix
The only way to truly solve this is to never let SAF I/O touch the JS thread at all. There are two realistic paths:

Path A — Keep SAF, move it to a native module (best long-term)
Write a tiny Android native module that does the SAF folder read in a background Java thread and returns the file list to JS. This is what WhatsApp status saver apps in the Play Store actually do.

Path B — Simplify the JS SAF path (faster to do, less perfect)
Strip out all the layers of defensive code that have accumulated (the polling, the multiple caches, the BFS re-walk) and replace it with a single, clean, minimal SAF reader. Accept that cold launch on bad OEM devices may take 2–3 seconds, but at least it doesn't completely freeze.

My honest recommendation
The app is not broken beyond repair. The structure is good. The problem is specifically that 6+ rounds of fixes on the same 2 files have made them fragile and hard to reason about.

What I would do: A targeted rewrite of only the Android 11+ SAF loading section inside MediaContext.tsx — keeping it simple, stripping the layers of defensive machinery that contradict each other, and testing one clean path instead of 5 fallback paths that may interfere.

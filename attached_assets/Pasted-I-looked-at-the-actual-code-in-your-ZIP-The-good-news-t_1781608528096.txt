I looked at the actual code in your ZIP.

The good news: this is **not a SAF issue anymore**.

Your viewer is already doing:

```txt
content://
↓
prepareStatusForViewing()
↓
copy to cache
↓
file://
↓
expo-video
```

So the old Android 11 SAF starvation bug has mostly been solved.

---

### The real clue

You said:

> plays → freezes → plays → freezes → plays → freezes

I found code that is literally capable of creating that exact pattern.

In `VideoPlayerView.tsx`:

```ts
player.addListener('playingChange', (event) => {
  if (event.isPlaying) {
    recoveryFired.current = false;
  } else if (
    hasCalledOnPlaying.current &&
    isActiveRef.current &&
    !recoveryFired.current
  ) {
    recoveryFired.current = true;

    setTimeout(() => {
      player.play();
    }, 80);
  }
});
```

Every time ExoPlayer reports:

```txt
isPlaying = false
```

your code force-calls:

```ts
player.play()
```

again.

---

### Why this is dangerous

On Android 11+:

```txt
Playing
↓
Buffering
↓
isPlaying = false
↓
Your recovery fires
↓
player.play()
↓
Buffering again
↓
isPlaying = false
↓
player.play()
↓
loop
```

Result:

```txt
play
freeze
play
freeze
play
freeze
```

Exactly your symptom.

### If the freezes remain

Then I would investigate:

1. `copyFileToCache()` speed
2. whether the cached file is fully copied
3. file size before playback
4. ExoPlayer buffering events
5. whether multiple `VideoPlayerView`s are active simultaneously
